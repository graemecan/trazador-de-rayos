Tarea13

Ingeniería del proyecto

Compilación separada y un Makefile

Objetivo

Convertir el proyecto en una estructura profesional: separar cada módulo en declaración (.h) y definición (.c), compilarlos por separado a archivos objeto .o y enlazarlos, todo automatizado con un Makefile.

Hasta ahora todo el código vivía en cabeceras (con static inline) y compilábamos con un único comando gcc main.c …. Fue una simplificación deliberada para no pelearnos con el sistema de compilación mientras aprendíamos el lenguaje. Ahora que el proyecto tiene ocho archivos, toca organizarlo como se hace en la práctica.

Concepto de C · qué hace realmente el compilador

Traducir un .c a ejecutable tiene fases:

  1. Preprocesado: se resuelven los #include y #define (se «pega» el texto de las cabeceras).
  2. Compilación: cada .c (una unidad de traducción) se convierte en un archivo objeto .o con código máquina.
  3. Enlazado (linking): todos los .o se combinan, resolviendo las referencias entre ellos, en un único ejecutable. La bandera -lm añade la biblioteca matemática en este paso.

La ventaja de separar: si cambias un solo .c, basta recompilar ese .o y volver a enlazar; no hace falta recompilar todo. En proyectos grandes esto ahorra muchísimo tiempo.

Concepto de C · declaración frente a definición

La clave de la compilación separada es dividir cada módulo en dos:

  • El .h contiene declaraciones: tipos y prototipos de funciones (la firma, sin cuerpo). Dice qué existe.
  • El .c contiene las definiciones: el cuerpo de esas funciones. Dice cómo funcionan.

Cualquier .c que incluya el .h sabe cómo llamar a la función; el enlazador encuentra el cuerpo en el .o correspondiente. Y quitamos el static de las funciones públicas: static significa «visible solo en este archivo», justo lo contrario de lo que queremos ahora.

¿Qué archivos siguen siendo solo cabecera?

vec3.h y rtweekend.h se quedan como están, con static inline. Son funciones matemáticas diminutas y muy llamadas: interesa que el compilador las «incruste» (inline) en cada sitio. static inline en una cabecera es la forma correcta y estándar de compartir esas mini-funciones entre varias unidades sin violar la regla de una sola definición. No todo tiene que ir a un .c.

Pista · «incluye lo que usas»

Al separar módulos aparece un fallo típico: main.c usaba fprintf y stderr, pero funcionaba solo porque <stdio.h> llegaba «de rebote» a través de otra cabecera. Al reorganizar, ese rebote desaparece y el compilador protesta: error: 'stderr' undeclared. La regla de oro: cada archivo debe incluir directamente las cabeceras de lo que usa, sin depender de inclusiones indirectas. Solución: añade #include <stdio.h> al principio de main.c.

Compilar a mano (para entender qué automatiza make)

Primero, cada .c a su .o con la bandera -c («compila, pero no enlaces»). Luego, enlazamos todos los objetos:

terminal
# Un objeto por cada unidad de traduccion
$ gcc -std=c11 -Wall -O2 -c main.c     -o main.o
$ gcc -std=c11 -Wall -O2 -c color.c    -o color.o
$ gcc -std=c11 -Wall -O2 -c hittable.c -o hittable.o
$ gcc -std=c11 -Wall -O2 -c material.c -o material.o
$ gcc -std=c11 -Wall -O2 -c camera.c   -o camera.o
# Enlazado final: todos los .o -> ejecutable "rt" (con -lm al final)
$ gcc main.o color.o hittable.o material.o camera.o -o rt -lm

Hacer esto a mano cada vez es tedioso y propenso a errores. make lo automatiza: describes las reglas (qué depende de qué y cómo construirlo) en un archivo llamado Makefile, y make recompila solo lo necesario.

Concepto de herramientas · anatomía de un Makefile

Una regla tiene la forma objetivo: prerrequisitos y debajo, los comandos para construirlo. make reconstruye un objetivo solo si algún prerrequisito es más reciente que él. Usamos variables (CC, CFLAGS) para no repetirnos, una regla-patrón (%.o: %.c) que sirve para todos los objetos, y variables automáticas: $< es el primer prerrequisito (el .c) y $@ es el objetivo (el .o).

archivo · Makefile
# Compilador y banderas: variables reutilizables
CC      = gcc
CFLAGS  = -std=c11 -Wall -Wextra -O2
LDFLAGS = -lm

# Los objetos que forman el programa y las cabeceras de las que dependen
OBJ = main.o color.o hittable.o material.o camera.o
HDR = vec3.h ray.h rtweekend.h color.h hittable.h material.h camera.h

# Objetivo por defecto (el primero): enlazar todos los .o en "rt"
rt: $(OBJ)
→$(CC) $(CFLAGS) $(OBJ) -o rt $(LDFLAGS)

# Regla-patron: cada X.o se compila de X.c. Si cambia alguna
# cabecera (HDR), se rehacen todos los objetos que dependen de ella.
%.o: %.c $(HDR)
→$(CC) $(CFLAGS) -c $< -o $@

# Atajos utiles
run: rt
→./rt > imagen.ppm

clean:
→rm -f $(OBJ) rt

# Objetivos que no producen un archivo con su nombre
.PHONY: run clean

El símbolo → marca dónde va un TAB real (ver la pista de abajo). No lo escribas: es solo para señalar la sangría.

Pista · el error más famoso de make: missing separator

Las líneas de comandos bajo cada regla deben empezar por un carácter de tabulación (TAB), no por espacios. Si usas espacios, verás Makefile:9: *** missing separator. Stop. Configura tu editor para insertar un TAB de verdad en los Makefiles (muchos editores convierten TAB en espacios por defecto).

Con esto, construir y ejecutar es inmediato:

terminal
$ make            # compila lo necesario y enlaza "rt"
gcc -std=c11 -Wall -Wextra -O2 -c main.c -o main.o
...
gcc -std=c11 -Wall -Wextra -O2 main.o color.o hittable.o material.o camera.o -o rt -lm
$ make            # nada ha cambiado
make: 'rt' is up to date.
$ touch material.h # simula editar una cabecera compartida...
$ make            # ...y make recompila lo que depende de ella
$ make run         # compila si hace falta y renderiza a imagen.ppm
$ make clean       # borra los .o y el ejecutable

Entrega y retos

  • El proyecto reorganizado en .h + .c, tu Makefile, y una captura de make construyéndolo.
  • Ejecuta make dos veces seguidas y muestra que la segunda dice «up to date».
  • Reto: añade un objetivo debug que compile con -g -O0 (para depurar con gdb) en lugar de -O2.
  • Reto: las dependencias de cabecera son «gruesas» (todo depende de todo el HDR). Investiga gcc -MMD para generar dependencias automáticas y precisas.
